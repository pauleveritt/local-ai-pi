# Phase 5 cycle 2 — the cost answer

**Date:** 2026-08-04
**Status:** design
**Phase:** 5 — the improvement loop

## Purpose

Test the claim that justified building `harness/telemetry.py` and has never
been tested with it: *getting an orchestrator to write handoff packets for an
implementer may consume more than the orchestrator simply doing the work
itself.*

Two n=16 batches on `AGENTCLINIC_PHASE_1` — one bare, one with the
`sdd-orchestrator` improvement. Cycle 1 built the mechanism and proved one
delegation works; this cycle spends the runs.

## Why a saturated workload is the right control

Bare Pi scored 16/16 on this suite in Phase 1, and the prior project's
orchestrated arm on the same detailed roadmap also scored 16/16. A success
rate that cannot move is normally a dead end. Here it is what makes the
comparison clean: with the verdict pinned on both arms, a difference in turns
or `context_processed` is attributable to the orchestration rather than to one
arm solving more of the problem than the other.

What an improvement *buys* is not observable here and belongs to cycle 3's
suite, which has headroom. *(Renumbered 2026-08-04: a telemetry cycle was inserted as cycle 3, so the suite is cycle 4 and tuning is cycle 5+.)*

## Pre-registered predictions

Written in cycle 1's spec before this mechanism existed, restated here
unchanged. Their source series carries a `PENDING RULE 8 REVIEW` banner: they
are predictions to replicate or falsify, never citable as results.

1. **Both arms accept 16/16.**
2. **The orchestrated arm's `context_processed` is higher.** A null or
   negative result is equally publishable and is the reason the cycle exists.
3. **Delegation occurs on 16/16 orchestrated runs.**

## The check cycle 1 makes mandatory

Cycle 1's spike found that an orchestrated run whose extension never loaded
still grades **accepted**, because the parent writes the solution itself once
the delegation errors. So a per-run delegation check is not optional
bookkeeping — without it, prediction 2 could be computed over runs that were
silently bare.

For every run in the orchestrated arm, recomputed from its captured stdout:

- at least one `tool_execution_end` with `toolName == "subagent"`;
- that call's `isError` is `false`;
- how many `subagent` calls were in flight at once.

A run failing the first two is reported as a **failed delegation**, counted,
and excluded from the cost comparison with the exclusion stated. The arm's
headline number is meaningless if this check is skipped or quietly passed.

## The observation that decides a Backlog gate

The Backlog gates building our own ~150-line subagent tool on "a measured run
shows the shipped extension contaminating or losing a measurement", because
the shipped extension can put parallel children on a single-threaded local
server. The third bullet above is that measurement. Neither of cycle 1's two
runs put more than one child on the server; this is the first real chance for
the gate to fire, and the result is recorded either way.

## Method

Both batches on the same machine, same model, same Pi, sequentially, with no
commit in the batch's working directory from any session between the first run
and the last — `_conditions` re-reads `HEAD` per run, so a commit aborts the
batch and strands the checkpoint. The freeze is agreed with the owner across
sessions, never self-imposed.

Checkpoints live outside version control in `~/local-ai-pi-evidence/`,
alongside the existing four. They are ~4–9 MB each and are evidence, not
source.

Batches are run in **resumable chunks** — `run_batch` with an increasing
`target`, appending to one checkpoint — rather than one long-lived background
process. Every invocation stays in the foreground. A backgrounded live run was
torn down mid-flight during Phase 4 cycle 1, and a run that dies leaves no
trace in the harness's records.

Comparison is by hand, per the phase's binding constraint. No comparison code
is written this cycle.

## Deliverable

A research record stating: both arms' accept counts, the delegation check's
result per arm, medians and ranges for turns and `context_processed`, each
prediction scored, and the parallel-children observation. Its per-run table is
generated by a committed recompute script, per Phase 2 cycle 4's claim
discipline, so the published table cannot silently diverge from its source.

## Out of scope

- Automated comparison, per the phase constraint.
- Parent/child cost attribution: the parent's `tool_execution_end` carries
  what this question needs.
- Any prompt or packet tuning. If the orchestrated arm performs badly, that is
  the result. Tuning is cycle 4+, under fresh pre-registration. *(Renumbered 2026-08-04: a telemetry cycle was inserted as cycle 3, so the suite is cycle 4 and tuning is cycle 5+.)*
